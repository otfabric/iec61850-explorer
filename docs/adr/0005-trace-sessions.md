# ADR 0005: Trace sessions analyse captures offline with go-mms-trace

- Status: Accepted
- Date: 2026-11-10

## Context

M4 adds trace analysis: a packet capture of IEC 61850 traffic (MMS on ISO-on-TCP, GOOSE, Sampled Values) is analysed, its gaps and failures are identified, its transactions are shown on a timeline, and what it names is correlated with an IED model (application correlation). The Explorer's own traffic should be inspectable down to the PDU (application-to-wire correlation). Decoding a capture means reading pcap and pcapng files, reassembling IP and TCP, framing TPKT and COTP, and decoding session, presentation, ACSE and MMS, all on untrusted input. The Explorer must not grow a protocol stack of its own (principle 2 of `docs/ARCHITECTURE.md`; the libraries carry the protocol code), and its daemon must stay pure Go (no cgo, no libpcap).

## Decision

1. **The engine of record is [go-mms-trace](https://github.com/otfabric/go-mms-trace)** (v0.1.1, MIT, same organisation). `trace.Analyze` reads a whole capture (pcap or pcapng, plain or gzip) and returns associations, transactions paired by invoke ID with a status and latency, InformationReports, GOOSE and SV streams with their sequencing issues, and counters of what it could not use. MMS is decoded by go-mms (`mms.DecodeTSDU`), GOOSE and SV by go-iec61850. The Explorer decodes nothing itself; a decoding gap is fixed in go-mms-trace or go-mms, not worked around.
2. **Offline only.** A trace session is a capture the user chose; the engine never captures live and never sends anything for a trace. Like SCL files and snapshots, the capture arrives as bytes the user interface read (the engine never opens a path), at most 256 MiB (`model.MaxTraceBytes`); a larger file is refused (`limit_exceeded`, like SCL files and snapshots). At most 4 trace sessions are open at once (`model.MaxTraceSessions`): the result stays in memory while its session is open.
3. **A trace session has no IED model.** It appears in the session tabs (`kind: trace`, state `offline`) and answers the trace views (summary, associations, timeline, reports, streams, findings) and trace exports; the model views (browse, read, data sets, compare, ...) refuse it (`invalid_argument`).
4. **Findings come from the analyser's fields.** Every finding names the go-mms-trace field, counter or status it is read from (`Association.Gaps`, `Transaction.Status=unanswered`, `Counters.TPKTResync`, `GooseStream.Issues["sqNum gap"]`, ...) and where it is (association, frame, time, stream). Nothing is inferred beyond those fields, as for connect diagnoses (principle 5).
5. **Correlation copies the linked model.** The user links a trace to a live, SCL or snapshot session. MMS names are mapped to IEC 61850 references (go-iec61850 `RefFromMMS`) and looked up in a copy of the linked session's model, data sets and control blocks, taken when it is linked (a live session's are read in Observe mode). A captured IEC 61850 report is decoded against the data set of its report control block only when the linked session defines both; otherwise its values are shown as captured. Members are never invented; an object the model does not have is a finding. A snapshot holds no definitions, and the trace says so.
6. **The wire view of the Explorer's own traffic** records the ISO units of a live session's associations with go-mms `DialOptions.RawHook`, which only observes the bytes the client sends and receives: it adds no service, so Observe mode (ADR 0002) and its tests are unchanged. Units are kept only while an operation runs, linked to it (`Operation.wire`), at most 256 units and 4 MiB per session; poll cycles keep none. They are decoded with `mms.DecodeTSDU` when the user asks, never logged. go-mms decodes only the authentication mechanism of an AARQ; the hex of an AARQ that carries authentication is not shown.

## Consequences

- The Explorer's trace analysis is as good as go-mms-trace's: its limitations ([LIMITATIONS.md](https://github.com/otfabric/go-mms-trace/blob/main/LIMITATIONS.md)) are the Explorer's. MMS over TLS is not decodable; MMS on a port other than 102 needs the port named when the capture is opened; GOOSE and SV are found on the Ethernet link type only; a TCP gap is counted per association, not located in time or by frame.
- go-mms-trace's evidence is its own tests on generated captures, on captures between independent stacks (libiec61850, iec61850bean, dscsystems, iec61850-rust, cB-Sigma) and on public captures, and a comparison with Wireshark's dissector that is run by hand and compares PDUs by kind, invoke ID and request service only (not values, object names, error codes, GOOSE or SV).
- A result is not bounded by the input's limits: it grows with the capture. 256 MiB of capture can take several times that in memory; the trace-session bound caps the total.
- The fields of a captured report (RptID, OptFlds, the optional fields, inclusion, data references, values, reasons) are decoded by go-iec61850 `DecodeReport` (v1.16.0, strict about the report format of IEC 61850-8-1) over the values go-mms decoded. In v0.10.0 the engine walked them itself, because go-iec61850's decoder was not exported; v0.10.1 uses the library's.
- Live capture stays out of scope: it would need privileges, raw sockets or libpcap, and a platform matrix the daemon does not have (go-iec61850's raw Ethernet is Linux and macOS only).
